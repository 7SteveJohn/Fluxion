# Fluxion

**Windows 游戏优化 + DLSS 帧生成管理**（v2.0 · 由 GameBoost v1.0.5 与 DLSSG-Tool v1.1.0 合并重构）

一句话：**一键把系统调到适合游戏的状态，并给 RTX 20/30 系游戏接上 NVIDIA 只给 40 系开的帧生成。**

---

## 1. 它解决什么问题

| 问题 | 本工具的答案 |
|---|---|
| 3A 游戏帧数低 | 电源/调度/GPU/网络/内存全方位优化 + **DLSS 帧生成**（3060 Ti 也能量） |
| 竞技 FPS 手感黏、延迟高 | 驱动配置自动化（低延迟=超高、电源=最高性能）+ 0.5ms 定时器（仅 FPS 档）+ 网络/网卡优化 |
| 二游/3A 着色器编译卡顿 | NVIDIA 着色器缓存=无限制 + 游戏期电源联动 |
| 黑屏/掉帧找不到原因 | nvlddmkm 崩溃取证、C 盘守护、网络哨兵、覆盖层规避 |
| 帧生成装了没用 | **运行诊断**：日志 + 进程模块双证据，直接告诉你代理有没有真正激活 |

```
Fluxion/
├── src/
│   ├── Core.cs      逻辑层：配置、优化执行、监控看门狗、游戏联动、NVAPI、备份/还原
│   ├── Dlssg.cs     帧生成模块：游戏扫描、代理装卸、入口选择、日志诊断、参数、下载
│   ├── Ui.cs        界面层：简约浅色 UI（系统标题栏 + 侧栏导航 + 白色分区 + 原生控件）
│   └── app.manifest UAC 清单：requireAdministrator（安装版必需）
├── compile.ps1      csc 编译脚本（三文件 + icon + manifest）
├── rebuild.bat      一键：编译 → 停旧实例 → 部署到 D:\Fluxion（便携版）
├── make_installer.bat  一键：构建安装包 Setup.exe（需 Inno Setup 6）
├── installer/       Inno Setup 安装脚本（Fluxion.iss）
├── check.bat        静态预检（不依赖编译器，编译前先跑这个）
├── config.json      全部开关与参数（优化项分节 + dlssg 段）
├── tools/           静态校验脚本（Python）
│   ├── static_check.py   语法合规/括号平衡/符号引用/重复成员/隐式转换/CS0136/CS0108
│   ├── member_check.py   自定义控件的成员访问（CS1061 风险，作用域感知 + 按基类自动推导）
│   ├── type_ref_check.py 静态类型成员引用（Theme./Native./Program./Dlssg.，CS0117 风险）
│   ├── layout_check.py   绝对坐标越界与兄弟控件相交（旧布局机制的兜底）
│   ├── orphan_check.py   孤儿控件与空分区（新布局机制的兜底）
│   └── iss_check.py      安装脚本校验（BOM/段名/引号转义/Source/Tasks/提权守卫）
├── legacy/          重构前的旧源码备份（仅存档，不参与编译）
└── icon/icon.ico
```

**分层原则**：UI 只管画和点击，所有系统操作都在 Core/Dlssg 里；UI 通过 `Program.ApplyAll()` 这一类编排方法调用逻辑，不再像 v1.x 那样把 13 个优化调用散在窗体的点击处理器里。

## 3. 编译与部署

```
双击 rebuild.bat
```

它会做四件事：编译 → 停掉正在运行的实例 → 部署到 `D:\Fluxion\` → 提示完成（首次部署时同时复制 config.json）。

- 编译失败会在 `compile_result.txt` 里留下完整 csc 报错，把这个文件发给助手即可定位。
- 启动需要管理员权限（要改注册表/电源/网卡）。编译产物带 UAC 清单（`src/app.manifest`，`requireAdministrator`），由系统在进程创建时弹一次提权确认、快捷方式显示盾牌；代码里原有的自提升逻辑现在只作兜底（已提权则自动跳过）。
- 配置文件已存在时**不会被覆盖**，你的自定义设置会保留。

### 编译前先跑一次静态预检（可选，30 秒）

```
双击 check.bat
```

它不需要编译器，只做静态扫描，能提前发现绝大多数低级编译错误：

| 检查项 | 对应真实编译错误 |
|---|---|
| C# 6+ 语法（`$""` 插值、`?.`、表达式体成员、`nameof`、`using static`） | CS1026 / CS1525 |
| 括号 / 花括号 / 方括号平衡 | CS1513 / CS1022 |
| 跨文件符号引用（`Program.X` / `Dlssg.X` / `Theme.X` 是否存在） | CS0117 / CS1061 |
| 同一类型内签名完全相同的重复成员（合法重载不报） | CS0102 / CS0111 |
| `new byte[long表达式]` 这类隐式转换（长→整型） | CS0266 |
| 自绘控件上的成员访问是否真的存在（作用域感知，避免同名局部变量误报） | CS1061 |
| 局部变量作用域冲突（外层变量 vs 嵌套块内同名变量 / `foreach`·`for`·`using` 头部变量重名） | **CS0136** |
| 自定义类成员与 WinForms 基类成员重名（遮蔽 `Control.Right` / `Panel.Tag` 等） | **CS0108** |
| 调用本项目自己的方法时实参个数不匹配 | **CS1501 / CS1729** |

两个脚本的判定规则都做过**反向测试**（人为注入已知错误，确认全部命中；再对真实源码跑出 PASS），所以 PASS 是有意义的信号，不是空转。反向测试不只是"能抓到"，还要**零多余告警** —— 探针应恰好报出注入的那几条。

- 用 `python tools/static_check.py src` / `python tools/member_check.py src` / `python tools/iss_check.py installer/Fluxion.iss .` 单独跑也行，退出码 0 = 通过。
- `python tools/syncheck.py` = **编译冒烟**（编成一个临时 library，只看编译器怎么说，不产也不替换任何产物）。
  它同时跑一段「runner 收尾自检」：19 个 `run_*.py` 必须统一用 `tools/_probe_runner.py` 的
  `finish(<探针进程>, verdict=True|False)` 收尾，且声明 `verdict=True` 的那些探针源码里必须有
  「按 FAIL 返回非 0」的那一行。**为什么值得单独盯**：这些 runner 曾经无论探针红不红都退出 0
  （"跑一遍全绿"其实是"跑一遍没看结果"），第一版补丁靠在模块全局里猜结果变量名 —— 谁改个
  变量名就又失效了。现在收尾只有一份实现，且必须显式传参。
- 注意：这是辅助手段，**不能替代编译器**。类型推断、重载决策、泛型约束等仍以编译器为准。

## 3.1 打包成安装包（要 setup.exe，不要便携版）

```
双击 make_installer.bat
```

产物：`installer_out\Fluxion-Setup-2.4.0.exe`（当前版本；带命令行的静默打包可用
`ISCC.exe /O<输出目录> installer\Fluxion.iss` 直接跑，本机 ISCC 在 `%LocalAppData%\Programs\Inno Setup 6\`）。

前置：先跑过一次 `rebuild.bat`（安装包直接用编译好的 `Fluxion.exe`）。机器上没有 Inno Setup 时，脚本会打印安装指引并询问是否用 winget 自动装（`winget install --id JRSoftware.InnoSetup -e`），也可以自己去 <https://jrsoftware.org/isdl.php> 下载。

安装包行为：

| 项 | 行为 |
|---|---|
| 安装位置 | `C:\Program Files\Fluxion`（64 位，安装时提权）。**建议保持默认**，别指到 `rebuild.bat` 的部署目录（见下方排错） |
| 快捷方式 | 开始菜单 +「创建桌面快捷方式」可选任务 |
| 开机自启 | 可选任务 → 建提权计划任务（`schtasks /SC ONLOGON /RL HIGHEST`），**不在每次登录弹 UAC**；与应用内「开机自启」开关共用同一任务名 |
| 数据目录 | 安装时创建 `C:\ProgramData\Fluxion\` 并放入 `config.json`（已存在则不覆盖） |
| 卸载 | 控制面板/「应用」里可见；**配置、日志、备份不会被删除**，卸载完成会提示路径 |
| 升级 | AppId 固定，再次运行新版本安装包即识别为升级覆盖 |
| 运行中安装 | 靠互斥体 `Fluxion_SingleInstance` 检测到程序在跑，会先要求关闭 |

### 便携版 vs 安装版（同一个 exe，运行时自动判断）

| | 便携版 | 安装版 |
|---|---|---|
| 判定条件 | exe 同目录有 `config.json` | 没有，且 `%ProgramData%\Fluxion` 存在 |
| 数据位置 | exe 同目录 | `%ProgramData%\Fluxion\`（config / logs / backup / dlssg） |
| 侧栏底部 | 显示「便携版」 | 显示「安装版」 |

之所以要分流：`Program Files` 是只读的程序目录。把备份和日志写在那里，卸载会被一并删除、升级也可能被覆盖 —— 而备份正是用来还原系统的，丢了就没意义了。
### 排错：安装末尾报「CreateProcess 失败；错误代码 740」

`Fluxion.exe` 带 `requireAdministrator` 清单，而 Inno Setup 的 `postinstall` 运行步骤**故意以原用户（未提权）身份**执行 —— 直接 `CreateProcess` 一个要求提权的 exe 会被系统拒绝，740 就是 ERROR_ELEVATION_REQUIRED。修法：给该 `[Run]` 条目加 `shellexec` 标志，改走 `ShellExecuteEx`，由系统接管 UAC 提示。

同一轮复查还修掉两个自己埋的隐患：

| 问题 | 原写法 | 现在 |
|---|---|---|
| 每次登录弹 UAC | 写注册表 Run 键（由 shell 启动，命中提权清单 → UAC） | 建提权计划任务，无提示；名字与应用内开关一致 |
| 卸载可能删掉真实备份 | `[UninstallDelete]` 删 `{app}\logs`、`{app}\backup` | 整段删除（万一安装目录被指到便携版目录，那段会连真实备份一起删） |

`tools/iss_check.py` 会在出包前把这些点全查一遍（BOM / 行尾 / 段名 / 引号转义 / 续行 / `[Files]` Source 存在性 / `Tasks` 引用 / AppMutex 一致性 / postinstall 提权守卫），并把转义后的真实命令行打印出来核对：

```
python tools/iss_check.py installer/Fluxion.iss .
```

> ⚠️ **不要把安装目录改成 `rebuild.bat` 的部署目录**（`D:\Fluxion`）。那是便携版/开发的输出目录：装进去会得到「已安装 + 便携」混合状态 —— 目录里同时有 `unins000.exe` 和便携版 `config.json`，程序会按便携版模式就地读写，而下次 `rebuild.bat` 部署又会覆盖已安装的 exe。安装包保持默认的 `C:\Program Files\Fluxion` 即可。

### 4.1 取值细调（v3.6.0）：具体档位交给你自己选

一键优化给的是「程序认为的最优值」，但很多项的最优值本来就因人而异（着色器缓存上限、DLSS 强制预设、
量子长度……）。所以 **v3.6.0 起，凡是「能给出具体档位」的项，档位全部摊开让你自己选**。

三个入口（都在「性能优化」页）：

| 入口 | 位置 | 用途 |
|---|---|---|
| 双击带 ⚙ 的行 | 优化项明细表 | 直接跳到该项的档位选择 |
| 「调整选中项」 | 表格上方按钮 | 同上，键盘 / 鼠标都顺手 |
| 「取值细调…」 | 表格上方按钮 /「自定义项」对话框 | 完整清单，18 项一次看完 |

体检表**总行数随环境变化**（驱动层要能读到 nvdrsdb、异类策略只在混合架构 CPU 上出现；
本机是 51 行）。其中 **19 行带 ⚙（可调）**，其余是只读核验 —— 表下方直接写明这个区分。

**18 个可调项**：着色器缓存开关 / 缓存大小上限（**12 档**：0、128MB、256MB、512MB、1GB、4GB、
5GB、8GB、10GB、16GB、100GB、无限制）/ DLSS 模型覆盖 / 强制预设字母 / 预设档 /
竞技档·预渲染帧数 / 竞技档·电源管理 / 竞技档·垂直同步 / 竞技档·纹理过滤质量 /
3A·MMO·二游档取值 / 后台帧率上限 / HAGS / Win32PrioritySeparation / 处理器最小状态 /
处理器最大状态 / 前台响应优先级 / Nagle / 网络流量节流。
另有「HAGS × 竞技游戏(A/B 建议)」一行也带 ⚙ —— 它与「硬件加速GPU计划(HAGS)」共用同一个旋钮。

**默认值 = 改造前的硬编码值**，所以升级后行为零变化 —— 只有你主动改了才会变。

**哪些坚决不给旋钮**：HPET 强制、GPU 中断绑核、MSI 强制转换、rBAR 全局强开、异类策略。
理由是多来源明确警告：这类项改错的代价是**设备从系统里消失**或系统起不来。
「给用户权限」不等于「给用户自毁按钮」—— 只读核验的价值是让你知道现状，不是让你去动它。

⚠️ 边界：驱动层取值写进 `nvdrsdb` 后**重启游戏才生效**；HAGS 与量子长度需**重启系统**；
把某项改回默认**不会自动撤销已写入系统的值**（例如 Nagle 已写进网卡）—— 整体回退用「恢复备份」。

### 4.2 v3.6.1：状态分档 + 表格观感（用户指出的两处）

**① 「HAGS × 竞技游戏(A/B 建议)」这一行为什么没反应、为什么顶着红徽章？**

它是**建议**，不是缺陷：只在「RTX 30/20 系 + HAGS 已开 + 有竞技档游戏」时出现，意思是「现状已是推荐值，但值得你自己 A/B 验一次」。v3.6.0 之前它有两个毛病：状态写的是 `🟡`，而界面只认 `✅`/`⚠️` 两种开头 —— **开头不是这两个的一律渲染成红色「需处理」**，于是这一行里写着「HAGS 已开」、徽章却在报错；而且它没挂可调键，双击没有任何反应。

现在状态分成四档，并且这一行也挂上了 `hags.enable`（看到「可以 A/B」就能当场切，切完要重启系统）：

| 徽章 | 含义 |
|---|---|
| 已生效（绿） | 当前值与优化目标一致 |
| 未生效（橙） | 该生效却没生效（系统更新 / 驱动重置） |
| **待确认（灰）** | **不是缺陷**：可选 / 不适用 / 读不到（DPC 计数器不可用、HAGS 的 A/B 建议……） |
| 需处理（红） | 读取失败或需要管理员权限 |

**② 滚动时「有的色块更白、更割裂」**

三个原因叠在一起，都已修掉：

| 原因 | 修法 |
|---|---|
| 行底色是**逐格**铺的（一格一个 `DrawSubItem`），格与格之间的 1px 接缝、最右列右侧的空档没人画 | 改到 `DrawItem` **整行铺一次** |
| 斑马纹是 `#FFFFFF` / `#F8FAFC`（只差 3%）：看不出「这是交替条纹」，只看得出「这些行颜色不一样」 | 去掉斑马纹，**所有行同色 + 底部一条极浅分隔线** |
| ListView 是原生控件，`Control.DoubleBuffered` 对它**无效** —— 滚动时先擦成白底再逐行重绘，中间那一帧就是一片更白 | 打原生扩展样式 `LVS_EX_DOUBLEBUFFER`（探针读回确认：扩展样式 `0x00010020`） |

顺带修掉一个自 3.x 就存在的隐性问题：自绘里判断「是否选中」用的是 `e.State` / `e.ItemState`，而实测在部分绘制路径下**它会把 Selected 位给到每一行**（`tools/ui_snapshot.py light lst 1` 可复现：控件里没有任何一行被选中，绘制回调里的 Selected 位却行行都有）—— 按它画，整个列表会被涂成「选中态」底色并给每行加一条绿色强调条，看起来就是「这些行为什么跟别的不一样」。现在改成读行自己的 `e.Item.Selected`。

## 5. 帧生成（DLSSG）模块

### 原理
NVIDIA 官方帧生成只给 40 系（SM90）编译了可执行内核；20/30 系（SM86/SM75）运行时里没有对应 cubin。本模块接入开源项目 `dlssg_for_sm86`：以 DLL 代理方式接管游戏对 `nvngx_dlssg.dll` 的加载请求，换成补齐 SM86/SM75 内核的运行时（AI 模型仍是 NVIDIA 原厂）。

### 使用流程
1. **设置页**确认下载代理（国内需 Clash/FlClash 的 7890 端口），点「下载运行时」
2. **帧生成页**点「扫描游戏」，列表会标出每个游戏是否集成 DLSS 帧生成（`nvngx_dlssg.dll` / `sl.dlss_g.dll`）以及是否自带 FSR3
3. 点选游戏 → 「开启选中」；不想要了「关闭选中」完全还原
4. 进游戏 → 画面设置 → 帧生成 → 选 **DLSS Frame Generation** → 关垂直同步、帧率上限设无限

### 参数说明
| 参数 | 取值 | 建议 |
|---|---|---|
| 架构 Router | SM86（30 系）/ SM75（20 系） | 按显卡选 |
| 内核类型 | PTX（驱动 JIT，通用）/ Auto / Cubin | 默认 PTX，异常再试 Auto |
| 光流精度 | 0 精确 / 1 近似 | 画质优先 0 |
| 最大生成帧 | 1/2/3 | **8GB 显存建议留 2**；实测这是上限，实际倍率由游戏请求决定 |
| 日志级别 | 0~3 | 排错调 2~3，日志在游戏目录 `dlssg_sm86\logs\*.jsonl` |

### 实测结论（写进代码里的经验）
- **Cyberpunk 2077 (2.31) 必须用 winmm.dll 入口**：该游戏导入 `version.dll` 但运行中从不调用其函数 → 代理的延迟初始化永不触发，表现为「DLL 在进程里、零日志、帧生成无效且掉帧」。换 winmm 后立即激活，实测基准 **135 → 190 帧**。本模块内置该映射并自动处理。
- **判定代理是否真的在工作**，唯一可靠依据是日志目录出现 `runtime_redirect` / `feature_created` / `evaluate` 事件 —— 「运行诊断」按钮会读日志 + 查进程模块，直接给结论。
- 代理加载了但没日志 → 点「换入口重试」换一个入口 DLL（游戏只加载不调用某个入口时，代理永不初始化）；日志出现但没补帧 → 等游戏内开启帧生成。
- ⚠ 本模块**不是**把 DLSS 帧生成转成 FSR3：代理换成的是 NVIDIA 原厂 DLSS-G 运行时 + 自研 SM86/SM75 内核。若游戏内只出现「FSR 帧生成」，那是**代理没被激活**（见上一条），不是它本来就只能给 FSR。
- **带内核反作弊的游戏（绝区零 / 鸣潮 / 终末地 等）自动改用 `d3d12.dll` 入口**（v2.1.0）：这类反作弊会按【文件名】拦掉 `version.dll` / `winmm.dll` 等常规入口（上游 issue #111），而 `d3d12.dll` 是 DX12 游戏必须加载的系统库，拦不掉。工具会落三件套（代理 + 系统原件 + 载体），框架细节见第 ⑮ 节。可在帧生成页用「反作弊游戏自动改用 d3d12 入口」开关关掉。
- 反作弊若把代理**改名隔离**（形如 `version.dll.1271877294`），文件不再被加载却白占 15 MB —— 点「清理残留」回收（「关闭选中」也会一并清）。
- 扫描识别到但被忽略清单挡住的游戏**会灰显在列表里**，选中点「开启选中」即可恢复收录（不会再静默消失）。

### 使用须知
- **必须开启 HAGS**（设置→系统→显示→图形→硬件加速 GPU 计划），本工具会检测并提示
- **基础帧低于 40 不建议开**：会明显发糊、延迟增大；先用 DLSS 超分把基础帧拉到 60 再开
- **竞技射击不要开**（CS2/Valorant/三角洲）：帧生成引入额外延迟，得不偿失 —— 这些游戏用优化模块即可
- 8GB 显存：1080p 2X 约需 320MB、1440p 约 490MB 显存余量
- 游戏更新覆盖代理文件后需要重新开启；代理只往游戏目录放 1~2 个文件（`d3d12` 入口为 3 个 + 1 个 ini），删除即还原，也可用 Steam「验证文件完整性」

### 5.4 判据与可见性：换一次包要改哪里（2026-09-21）

代理包每发一版，"这一版是什么"这件事在本工具里分成三层，缺一层就会出现
"代码说 0.3.5、磁盘还是 0.3.2" 而无人发现：

| 层 | 位置 | 谁会读它 |
|---|---|---|
| 判据（体积档 / 入口名单 / 签名白名单 / 版本结论） | `%ProgramData%\Fluxion\catalog.json` | `Pack.Classify`、`Dlssg030.IsProxySize/CodeOf`、`ProxySign.Of`、`Plan.OwnerOf/EntryNames` |
| 磁盘事实（资源包里那份到底多大、是哪一版） | 量出来的，不存 | 帧生成页「运行时状态」第三行；`Dlssg030.PackActual()` |
| 导入账本（哪来的、什么时候、每个文件体积 + sha + 指纹） | `%ProgramData%\Fluxion\dlssg030-pack\pack.json` | 只由「拖入导入」写；`PackActual()` 读它比对 |

- **判据外置**：`catalog.json` 缺失或读不动时一律回落代码里的内置默认，并在启动日志写一行
  `判据来源：…` —— 读坏了静默用默认值是最难查的那类错，所以必须留痕。
  这份文件**没有界面入口**（它属于开发期手段，不该占用户界面）：要改就照 `Catalog.DefaultJson()`
   输出的形状手写一份，存盘即生效、不用重新编译；删掉它就回到内置默认。
  字段：`proxy.ver` / `proxy.bands[]`（体积→哪一版，闭区间）/ `proxy.windows[]`（是不是本方案，
  开区间）/ `proxy.legacy`、`proxy.sourceSize`（旧版 0.2.x 的两个窗口）/ `proxy.entries[]` /
  `proxy.signs`（作者与 NVIDIA 两张证书的指纹）/ `knowledge[]`（只在某些版本成立的上游实测结论）。
  给新版本加档时 **bands 与 windows 要一起加**：`IsProxySize` 只看 windows，
  只加细档会出现"代号认得、体积不认"。
- **知识条目集中在 `knowledge[]`**：UI 里那句"绝区零要不要伪装"以前是按版本手改文案，
  同一个结论在 `功能缺口与路线图.md` 里还有几处。现在由 `Catalog.Knowledge(id)` 按当前
  `proxy.ver` 挑那一条成立的，挑不出来就退回中性说法（宁可少说一句，不要说错一句）。
  其中一条就是升级路径：**别按版本号顺序升级** —— 0.3.3 让 NVIDIA 自家 NGX 模型也吃到
  架构改写导致 GPU 挂起（上游 #535/#538/#540/#542），0.3.4 才修；可升级路径只有 0.3.2 或 0.3.5+。
- **入口巡检**：帧生成页「停放遗留项」旁边那行会说清"这个目录里有几套代理并存"。
  两代代理同时在场 = 两套帧生成抢同一个入口（插件打架那一类故障），以前只有点部署才会顺带处理，
  平时看不见。巡检是只读的；停放只把文件改名成 `<原名>.parked.<方案>`，不删文件。
- **备份与回收**：部署 / 换包 / 卸载会往 `dlssg030-pack\_backup`、`xess-pack\_backup`、
  `xess-pack\_removed` 里堆东西（2026-09-21 实测 1.48 GB / 15 项）。设置页「备份与回收」
  按归属统计占用，回收一律**送回收站**，并且每个归属（整包一份 / 每个游戏一份）里
  **最新那一份永久保留** —— 卸载和换方案回滚要读的就是它。
  - 「回收范围」下拉的每一项后面会回填**当前统计出的条数与体积**。这不是装饰：默认档是 30 天，
    而刚换完包留下的备份通常只有几天 —— 不回填的话用户看到"点了没反应"，只会以为功能坏了。
    真要清那 1 GB 得选「7 天前」或「不限时长」（保留策略保护的那 484 MB 仍然不动）。
  - 两个不可逆感最强的确认框（「送回收站」「停放遗留代理」）默认键是**取消**，
    手快连按两下不会把东西清掉；两个动作本身都可逆（回收站可还原 / 停放只是改名）。
  - **刻意没做的事**：日志目录（`logs\`，本机 931 个文件 / 1.3 MB）不做回收入口 ——
    为 1.3 MB 多一个按钮 + 一套接口不值得，这是"别把工具做冗余"的一条。
- **`dlssg\source\` 只放旧版 0.2.x 的下载源件**（体积 15.5~15.8 MB，配套 `altnative\`）。
  0.3.x 走 `dlssg030-pack\{common,alts}`，不读这个目录。`SourceReady()` 现在除了
  `File.Exists` 还校验体积：源位上躺着 0.3.x 的件时不再误报"运行时已就绪"，
  并且界面上会写明为什么不算。

## 7.1 v2.0 首版的六个真实缺陷（已修复，务必重新编译）

### ① 满屏白块 + 红叉 —— 共享缓存字体被 `using` 释放（真凶）

**现象**：启动后左栏导航、右侧 CPU/内存/GPU 进度条、若干卡片出现白底方块（WinForms 的绘制失败标记）。

**根因**：`Theme.F()/FB()/Mono()` 返回的是**全局共享的缓存 `Font` 实例**（缓存本身是为了不泄漏 GDI 句柄），
但首版有 **10 处**写成 `using (var f = Theme.FB(10f)) { … DrawString … }` —— `using` 结束会 **Dispose 掉这个共享字体**。
此后所有同字号的绘制都在**已销毁的 GDI 句柄**上操作，GDI+ 返回 `InvalidParameter`，抛出 `ArgumentException: 参数无效。`；
WinForms 对 `UserPaint` 自绘控件绘制失败的兜底，是把该控件区域填成系统色并打叉。

**证据**：程序自己的日志每次启动都有**恰好 14 条** `UNCAUGHT_THREAD: ArgumentException: 参数无效。`；
而同时刻旧版 v1.0.5 的日志里**一条都没有** —— 直接锁定是**界面层新引入**的，与此前怀疑的"显示管线伪影"无关。

**修法**：10 处全部改为普通局部变量（缓存字体永不 Dispose）；`Theme` 字体缓存处加了醒目警告注释；
`tools/static_check.py` 新增 **CACHED-FONT-USING** 规则兜底（已做反向测试），以后再犯会在编译前被拦下。

| 影响面 | 说明 |
|---|---|
| 10 处 | `Card` 卡片标题、`NavBtn` 导航图标、`StatBar` 标题与数值、`Chart` 标题、`RowItem` 徽标/副标题/右侧标签、自绘标题栏主副标题 |
| 连带受害者 | 所有 `Font = Theme.F(8.5f)` 等被赋值过的 Label / ComboBox / TextBox（字体实例被别人的 `using` 销毁） |

### ③ `rebuild.bat` 对安装版会误判成便携版

### ⑤ 各页面 UI 错位 + 色偏（已修复，根因是 DPI）

反馈截图：标题栏出现 `Fluxion优化` 这样的**重影**、各页文字压在一起 / 被裁掉半句、下拉框里有发白的方块。

### ⑥ 编译失败 `CS0136: 不能在此范围内声明名为"box"的局部变量`

**报错原文**（`compile_result.txt`，用户机器上跑出来的）：

```
COMPILE_FAIL: csc failed: src\Ui.cs(547,21): error CS0136:
不能在此范围内声明名为"box"的局部变量，因为这样会使"box"具有不同的含义，
而它已在"父级或当前"范围中表示其他内容了
```

**根因**：`FlatCheck.OnPaint` 里第 506 行已经有 `var box = new Rectangle(0, by, bs, bs);`（复选框方框），
第 547 行在 `using (var b = …) { … }` 块里又写了 `var box = new RectangleF(…)`（标签文字框）。
C# 里**局部变量的声明空间是整个所在块**，嵌套块内不允许出现同名局部变量 —— 与谁先谁后无关。

**修法**：内层改名为 `textBox`。

**为什么校验器没拦住（这是本条的真正价值）**：`static_check.py` 里 CS0136 规则**曾经存在且能跑**，
但它给"两个同名声明所在块互为嵌套"额外加了一个前提 —— **外层声明必须晚于内层声明**。
而实际发生的是最常见的形态：**外层先声明、内层后声明**，于是这条规则在真实案例上给出了 PASS。
已删除该顺序条件（嵌套关系本身就足够判定），并把报错位置改指向**内层**那一处，
使行号与编译器一致（编译器报 547，校验器现在也报同一处）。

顺带补上同一漏洞的另一半：**局部变量与方法参数同名**（`void M(int x) { int x = 1; }`，同样是 CS0136），
以前完全没检查。两条规则都做了注入回归验证，且真实源码零误报。

**还有一个会让人白跑一趟的缺陷**：`rebuild.bat` 原来靠 `if not exist Fluxion.exe` 判断成败 ——
但**上一次编译出来的 exe 还在**，所以编译失败时它会打印 `OK` 并把**旧 exe** 复制过去，
用户看到的是"编译成功、程序没变化"。现已改为：编译前删掉旧报告 → 看 `compile.ps1` 退出码 →
再从 `compile_result.txt` 里确认出现 `COMPILE_OK`，任一不满足就打印**真实编译器输出**并中止。

> - **新增 `tools/type_ref_check.py`**：静态类型的 `Type.Member` 引用校验。之前只校验
>   `Program / Dlssg / Config`，本轮往 `Theme` / `Native` 里加了不少成员（`S/SF/Prep/Fit/TextTop/SFLeftPublic`…），
>   这些引用**全部绕过校验**（这正是"编译器报 CS0117 之前完全没提示"的盲区）。现覆盖 5 个类型。
> - **修正 `type_ref_check.py` 自身的剥离器 bug**：第一版用正则先删注释再删字符串，于是字符串里的
>   `//` `/*` 被当成真注释，一路吞掉后面的代码 —— `Program` / `Dlssg` 两个类型直接被吞成"未找到"（假阴性）。
>   已改为单遍扫描、字符串优先、等长空白替换（与 `static_check.py` 的实现等价）。
> - `check.bat` 从 4 步扩到 5 步：syntax → member → **type-ref** → layout → installer。

### ⑦ 简约浅色界面重做（第三版，2026-09-11）

**为什么要换**：深色版的错位与色准问题修了三轮仍有残留，根因不在"哪个坐标写错了"，而在**路线本身**：

| 自绘标题栏 | 拖动、圆角 Region、最小化按钮三处都要自己实现，且窗口比工作区大时还要额外收口 |

5. **系统标题栏**，不做自绘标题栏；时钟移到右下状态栏（由 1 秒定时器刷新）。

   仍然支持数据目录下放 `ui.scale` 覆盖倍率。
7. **页面可滚动**：内容超过窗口高度时出现滚动条，不会再有"控件被父容器裁掉看不见"的问题。

- **关闭窗口不再收进托盘** —— 旧版 `FormClosing` 挂在自绘标题栏里，换掉标题栏时一起丢了；

### ⑧ 静态检查全绿 ≠ 能编译：真实编译才是唯一判据（2026-09-11 深夜，同一天第二次）

第 ⑦ 条做完后，六个静态检查（syntax / member / type-ref / layout / orphan / installer）**全部 PASS**，
但真编译器一句话就否了：

```
src\Ui.cs(1239,30): error CS1061: "Fluxion.Sec" 不包含 "Resync" 的定义
```

**两个配套缺失**（⑦ 里描述的功能其实一直是空转的）：

- `Sec.Resync()` **只有调用、没有定义** —— 第 ⑦ 条写的"说明文字变长不会被裁掉"从未真正生效。
- 更隐蔽的是：`SetBody()` 靠 `l.Tag as Sec` 反查所属分区，而 `Sec.Body()` **从没给标签订过 `Tag`**。
  就算把 `Resync()` 补上，`s` 仍然是 `null`，照样静默失效。

也就是说：**"改了 12 处调用"只说明调用点改对了，不说明被调用的东西存在。**

#### 顺带修掉 `member_check.py` 的两个盲区（这才是放走 bug 的直接原因）

| 盲区 | 表现 | 修法 |
|---|---|---|
| **强制转换式声明从不登记** | `var s = l.Tag as Sec;` 之后 `s.任意东西` 全部不校验 —— `s.Resync()` 正是这样溜过去的 | 补 `v = ... as T` 与 `v = (T)...` 两类声明（转换目标即确定类型，无推断误差） |
| **控件字段（跨方法访问）从不校验** | 旧注释写的是"找不到声明就跳过，不臆测"，但本项目控件**几乎全是字段**：一个方法里 `new`、另一个方法里用。实际等于放掉了一大半访问点 | 新增类字段类型表：类体顶层 `Bar barCpu, barMem, barGpu;` 这类只声明不初始化的字段也登记类型 |

覆盖数从 **155 处**升到 **191 处**（新增的 36 处全是字段路径）。建字段表时又踩了一个自己挖的坑：
`Pg[] pages` 的元素类型是 `Pg` 但不是 `Pg`，`pages.Length` 合法 —— 按元素类型校验会误报，已显式跳过数组字段。

**反向验证（三个探针 3/3 命中，基线 PASS）**：

```
探针一  as 强转 + 不存在的方法   -> Ui.cs:1251  s.ResyncX_Probe (var s : Sec)     CS1061 risk
探针二  (T) 强转 + 不存在的方法  -> Ui.cs:1251  s.ResyncY_Probe (var s : Sec)     CS1061 risk
探针三  控件字段跨方法访问       -> Ui.cs:1368  spCpu.PushX_Probe (var spCpu: Spark)  CS1061 risk
数组误报防回归：基线里 Ui.cs 有 3 处 pages.Length（Pg[] 字段），基线仍 PASS
```

#### 结论：编译这件事**做得到**，别再以"沙箱编不了"为由跳过

Bash 通道会被安全策略拦下（`csc.exe` 被视同"可编译任意代码"，等同于 `Add-Type`），
但 **PowerShell 通道可以正常调起 `compile.ps1`** —— 本次就是这样编出 `COMPILE_OK` 的。

所以流程调整为一句话：**改完源码 → `check.bat` 六项预检 → 真编译一次 → 才敢说"改好了"。**
静态检查的定位是"提前预警、缩小范围"，**它永远是编译器的补充，不是替代品**。

另外 `rebuild.bat` 的第 2~4 步（停进程 → 拷到 `D:\Fluxion` → 拷图标）不需要编译器，可单独执行。

### ⑨ 2.0.3：扫描精度 + 自定义游戏增删 + 两项「未生效」修复（2026-09-12 凌晨）

**用户反馈三件事**：① 扫描把一堆非游戏收进列表（Clash Verge / Context Menu Manager Plus / dotnet / FlClash / Git / GitHub CLI）；
② 希望能手动添加/删除游戏路径；③ 「网络流量节流」「异类线程调度策略」两项一键优化后仍显示未生效。

#### ③ 先说两项「未生效」—— 都是 apply/check 的低级错，且都被 `WriteReg` 的 catch 吞了

| 项 | 根因 | 修法 |
|---|---|---|
| 网络流量节流 | `WriteReg(..., 0xFFFFFFFF, DWord)` —— **`0xFFFFFFFF` 是 `uint` 字面量**，而 `RegistryKey.SetValue` 的 DWord 只收 `int`，直接抛 `ArgumentException` 被吞 → 注册表里根本没写进去（实测回读确认"NOT SET"） | 改传 `-1`（int），落盘即 0xFFFFFFFF |
| 异类线程调度策略 | apply 和 check 用的 GUID `93b8b6dc-…` **这台机器上不存在**（`powercfg /q` 报"指定的电源方案、子组或设置不存在"，错误被吞）；真正存在的设置是 `bae08b81-…` = **异类短运行线程调度策略（SHORTSCHEDPOLICY）**，游戏线程正是短运行线程 —— 旧版 apply 实际只把它设成了一半，check 却查着那个不存在的 GUID，永远返回"?" → 永远显示未应用 | apply/check 全部对齐到 `bae08b81`，并**当场回读**确认（AC 索引实测已是 1 = 高性能处理器/P 核） |

> 排查方法值得记：别猜。直接在目标机上 `powercfg /q SCHEME_CURRENT SUB_PROCESSOR` 枚举 + 注册表回读，两个"未生效"的根因 5 分钟就实锤了。
> 顺带：`0x00000001` 在这套枚举里是"高性能处理器"（强制 P 核），`0x00000002` 才是"首选高性能处理器"——旧版注释把 1/2 标反了。

2.0.7 的日志明明已经给出了答案，甚至给出了操作指引：

```
[11:56:35] 扫描完成：识别 11 个游戏目录
[11:56:35] >>> 扫描完成：游戏目录 10 个，其中集成 DLSS 帧生成 4 个
```

但 `Ui.cs` 里这一行：


`btnIgnored` **只声明、从没 `new`、也从没进过任何 `Buttons(...)`**；配套的 `ShowIgnoredDialog()` 全文件**没有任何调用**。
结果就是：按钮在界面上根本不存在，而日志让用户去点它。—— 编译通过、四个静态校验器全 PASS、功能静默消失。

- `btnIgnored` 实例化并接线 `Click -> ShowIgnoredDialog()`；按钮排布改**两行**
  （`FlowLayoutPanel` 设的是 `WrapContents = false`，6 个按钮塞一行会在 1056 宽的窗口里溢出被裁掉）：
  - 第一行：`开启选中` / `关闭选中` / `添加游戏…` / `移除选中`
  - 第二行：`运行诊断` / `忽略清单`
- 「移除选中」补**二次确认**——它就是原神进忽略清单的来源，且是列表里唯一有持久副作用的动作，
  确认框里直接写明"不会删文件 / 怎么恢复收录"

#### 工具链补漏：`orphan_check.py` 从 2 类检查扩到 4 类

这个 bug 能出厂，是因为校验器只覆盖了「局部控件建了就扔」和「分区没挂上」，
**没覆盖类字段**和**私有方法**。新增：

| 新检查 | 含义 |
|---|---|
| `DEAD-FIELD` | 控件/组件类型的**类字段只声明、从未赋值** → 控件不存在 |
| `DEAD-METHOD` | 方法**定义了但全文件没有任何引用** → 入口没接线（用"总出现次数 ≤ 1"判定，委托传参也算引用） |

**验证方式**：拿一份把本次修复回退掉的 `Ui.cs` 副本跑新校验器，两条都被抓出来：

```
fields scanned : 49      methods scanned: 63
RESULT: 2 suspect item(s)
  - Ui.cs:541   DEAD-FIELD -> FlatBtn btnIgnored 只声明、从未赋值（控件不存在，功能静默消失）
  - Ui.cs:1755  DEAD-METHOD -> ShowIgnoredDialog() 定义了但全文件没有任何引用（入口没接线）
```

> 教训：**"声明了"不等于"存在"**。自绘 UI 的失效模式是"代码在、界面没有"，
> 而编译器对未赋值的字段、未被调用的私有方法一声不吭 —— 必须由静态检查兜住。

| 本工具接的是什么 | 社区项目 **`dlssg_for_sm86`**（`github.com/sdli1995/dlssg_for_sm86`）：给 Ampere/Turing **补一份 SM86/SM75 内核**，并内嵌 NVIDIA 自己的 DLSS-G 运行时 |
| 它跑的是什么管线 | **NVIDIA 原生 DLSS 帧生成**（含 2X/3X/4X），不是 FSR 转发。ini 里 `Router=SM86` 指"路由到 SM86 内核" |
| 「官方不支持」的含义 | NVIDIA 官方确实不给 20/30 系开放 DLSS 帧生成（`GpuSupportsDlssFg()` 判断的就是这一层）—— 但**官方不支持 ≠ 用不了**，本工具存在的意义正是绕开这条 |
| 那"注入后还是 FSR"是怎么回事 | **代理没被激活**：入口 DLL 只被游戏加载、从未被调用时，代理永不初始化，游戏内自然只剩它自带的 FSR 帧生成 |

> 铁证是项目自己的文件头注释与源码地址：`接管游戏对 nvngx_dlssg.dll 的加载请求，换成补齐 SM86/SM75 内核的运行时`；
> 代理容器 `source\version.dll`（15.7 MB）与 `source\altnative\{winmm,dxgi,dinput8,winhttp}.dll` 体积一致，
> 正是该项目 0.2.4 的产物。感谢用户坚持 —— 上一版结论是错的。

**先例**：CP2077 对 `version.dll` **只加载不调用**，代理延迟初始化永不触发（DLL 在进程里、零日志、FG 无效），
换成 `winmm.dll` 后立即激活，实测 135 → 190 帧。二游大概率是同一类问题，所以这版加了「换入口重试」。

#### 改动二：被忽略的游戏不再从列表里消失（原神那个问题）

2.0.7/2.0.8 的做法是「被忽略就不显示，日志里提一句」—— 用户视角仍然是"识别不出来"。

| 位置 | 行为 |
|---|---|
| 游戏列表 | 灰显 + `[已忽略]` 前缀，状态列写「已忽略（选中点「开启选中」即恢复收录）」 |

#### 改动三：注入前的收益/风险评估重写

去掉两条错误判据（`HasFsr3 → 注入零收益`、`显卡不支持 DLSS FG → 注入也只能得到 FSR3`），改为：

| 判据 | 维度 | 结论 |
|---|---|---|
| `GachaWords` 命中 | 反作弊 | 内核反作弊（mhyprot / HoYoKProtect / ACE）→ **封号风险**，最高优先级；社区已记录 ACE 直接拦截代理 DLL 加载的案例 |
| `!g.HasFrameGen` | 能力 | 目录里没有 `nvngx_dlssg.dll` / `sl.dlss_g.dll` → 没有可接管的调用，装了不生效 |
| `GpuSupportsDlssFg() == false` | 路径 | 走的是社区补内核方案（非官方），可能选项不出现 / 崩溃 / 画面异常，NVIDIA 更新后可能失效 —— **但不是"没用"** |

#### 改动四：帧生成页常驻说明重写（`HardwareFgNote`）

写清三件事：① 跑的是 NVIDIA 原生 DLSS-G，不是 FSR；② 生效判据 = 游戏内出现「DLSS 帧生成」+ `dlssg_sm86\logs\*.jsonl` 有 `runtime_redirect` / `feature_created` / `evaluate`；
③ 只有 FSR 选项时该做什么（换入口）。并明确提示：**帧生成只提高显示帧率，不会降低延迟**，想要低延迟请开 Reflex 并保证基础帧率。

#### 改动五：修掉静态校验器的一处真实缺陷（可空返回类型）—— 2.0.9 的有效部分

`static_check.py` 的 `MEMBER_RE` / `RE_METHOD_DECL` 与 `orphan_check.py` 的方法白名单都不认可空标记 `?`，
于是 `public static bool? GpuSupportsDlssFg()` **整条不被登记**，引用处被误报 `UNRESOLVED`，
`DEAD-METHOD` 检查也会静默失效。补上可选 `?` 后：

```
修复前：RESULT: 1 issue(s)  - UNRESOLVED Dlssg.GpuSupportsDlssFg (referenced in Ui.cs)
修复后：RESULT: PASS - no static issue found
```

**验证修复没有放松检测**：把 `Dlssg.HardwareFgNote()` 改成不存在的名字跑，仍报 `UNRESOLVED`（exit 1）；还原后 PASS。

> 教训一：**校验器自己也会漏**。出现新语法（可空类型、泛型…）时先确认校验器的正则认得它，否则"全绿"是假的。
> 教训二：**别把"官方不支持"写成"技术上做不到"**。差之毫厘，用户照着做就会得出错误结论。

### ⑮ 2.1.0：d3d12 复合入口 —— 反作弊游戏唯一能进的那条路（2026-09-13）

**背景**：绝区零、鸣潮在 2.0.x 里怎么换入口都不生效。上游 issue #111 给出了原因，而且是实测结论：

> 绝区零的反作弊会识别到 `version.dll` 等的名词，从而使其失效。

issue #387（同日，明日方舟：终末地）逐条重现了同样的症状 —— 5 个入口要么报"非法劫持模块"、要么能进游戏但菜单里没有选项。**这是国产二游 ACE 类反作弊的通用行为，不是操作错误。**

#### 路线：d3d12.dll 拦不掉

`d3d12.dll` 是 DX12 游戏**必须加载**的系统库，反作弊没法按文件名拉黑它。但上游 `dlssg_for_sm86` 只发 5 个入口（README 原话："五种已签名代理入口保持不变"），没有 d3d12 —— 所以本版自己造一个。

#### 实现：3,584 字节的纯 PE 代理（内嵌在 exe 里）

| 表 | 内容 | 作用 |
|---|---|---|
| 导出表 | 系统 d3d12.dll 的全部 **18** 个函数 → 转发到 `d3d12_orig.dll` 同名函数 | 对游戏完全透明，D3D12 调用照常落到微软签名副本上 |
| 导入表 | `dinput8.dll!DirectInput8Create` | Windows 加载代理时必须先解析它 → 自动把上游的 `dinput8.dll`（15.6 MB，真正的帧生成运行时）拉进进程 |

安装时落三个文件（**三件套，缺一件游戏启动即崩**）：

```
d3d12.dll         3,584 B   代理（本工具内嵌字节：导出转发 + 导入载体）
d3d12_orig.dll  146,176 B   转发目标 = 本机 C:\Windows\System32\d3d12.dll 的副本
dinput8.dll  15,666,496 B   载体 = 上游 altnative/dinput8.dll（一个字节没改）
```

与"抖音那条路"的差别：那边需要一个第三方 ASI 加载器把 DLL 注进去；这边靠 **Windows 自己的导入解析机制**把 dlssg 拽进来，不需要加载器，也不需要编译器。

#### 改动清单

| # | 改动 | 位置 |
|---|---|---|
| 1 | `D3d12Entry` / `D3d12Orig` / `D3d12Carrier` 三个常量 + 内嵌代理字节 `D3d12ProxyBlob` | `Dlssg.cs` |

### ⑯ 2.1.1：显卡名伪装 —— 第 1 层"菜单露出"的一键开关（2026-09-13）

**真机首测发现的问题**（2.1.0 部署到绝区零/鸣潮后）：鸣潮代理激活成功（日志 `configuration` + `ngx_driver_connected`，ACE 没拦 d3d12 链路），绝区零被 HoYoKProtect 掐在加载前（连日志都没有）。但两个游戏菜单都**没有帧生成开关**。

- 一键全部替换为 `NVIDIA GeForce RTX 4070`；原值完整备份到 `ProgramData\Fluxion\disguise.json`
- 再点一次按钮即从备份逐条还原；状态行常显"真名 / 伪装中"
- 全局可见（设备管理器/DXDiag/WMI 都显示 40 系名），杀软可能告警，驱动更新会重置注册表

**诚实声明**：能否骗过具体某个游戏取决于它读不读这些键值——NVAPI 走内核 ioctl 的判定改注册表无效。这是实验性功能，效果要真机验证（鸣潮是首选目标，绝区零第 3 层已死，伪装无意义）。

| 卡片图**好糊** | 取图标用的是 `Icon.ExtractAssociatedIcon()`，它只返回 **32×32**，拉到 132 的卡片上就是一团糊 | 改 `PrivateExtractIcons` 主动要 **256×256**，在多个候选尺寸里取实际像素最大的一张；缩放统一走 `GameIcon.Scale()`（HighQualityBicubic + TileFlipXY）。实测：鸣潮/绝区零/2077/极限竞速 + F:\黄油 全部游戏 32×32 → **256×256** |
| 页面**中部整片空白**、只显示底下一个分区、还多出横向滚动条 | ① `Pg` 容器没开双缓冲，而子控件全开了 —— AutoScroll 滚动是位图位移，父子缓冲不同步就留空白带；② `Reflow()` 在忙时把再入请求**直接丢弃**，尺寸变化永久丢失，布局停在半成品；③ 没给竖向滚动条预留宽度，竖条一出现就把内容挤出横条 | `Pg` 开双缓冲 + 重排改「挂起标记 + 迭代到收敛」+ 按竖条可见性预留宽度；`OnScroll` 强制整页重绘；封面网格换双缓冲子类 `BufferedFlow` |
| 鸣潮「可接入」到底是哪个插件 / 绝区零用的什么方案 | 卡片状态只写了泛化词：`可接入` = 目录里**有 DLSS 帧生成组件**（不代表装了任何插件）；绝区零那条 `已开启（d3d12.dll）` 是 **state.json 里的旧记录**在作祟（15:34 装的 3.5 KB 代理早被 XeSS 套件的 25.6 MB `d3d12.dll` 取代） | 卡片状态改为读**实际方案**：`XeSS 多帧生成（d3d12）` / `XeSS 多帧生成（dxgi）`；新增 `PruneStale()` 扫描前清理失效记录（判据是体积，不是「文件在不在」）；统计口径不再用「可接入 N 个」而按方案分列 |

顺带加的护栏：这两个游戏装了 XeSS 套件时，「关闭选中」会**拒绝执行**并提示改用「XeSS 多帧生成 → 卸载」——两者入口文件同名（`d3d12.dll` / `dxgi.dll`），混用会留下装了一半的状态（旧的 `libxess`、`fakenvapi` 还在，游戏可能起不来）。

封面库：数据目录 `covers\` 现在会在启动时自动创建；把图片按「卡片标题.png」放进去即自动用作封面，没放则用 exe 图标。

### ㉓ 2.6.0：视觉体系重做（圆角 + 深色主题）与封面管线修复（2026-09-14）

用户三条反馈：**有的游戏没封面**、**边角太锋利（希望沿用《游戏启动器》的美术语言）**、**标题与页面一体性差**。
逐条定位到代码级根因，并按"离屏渲染亲眼核对"的方式验证。

#### ① 圆角体系（这是"边角太锋利"的正解）

游戏启动器的 token 是 `--radius: 14px`（卡片）/ 11px（按钮）/ 10px（输入）/ 999（胶囊）。本版把它移植成一等公民：

| token | 值 | 用在哪 |
|---|---|---|
| `Theme.RCard` / `RPanel` | 14px | 游戏卡片、内容分区 |
| `Theme.RBtn` | 10px | 按钮、侧栏导航胶囊 |
| `Theme.RField` | 10px | 输入框、下拉框 |
| `Theme.RPic` | 10px | 卡片封面 |

新增自绘控件（原生控件画不了圆角，这是根因）：

- `CoverBox`：圆角裁切的封面框（原来是 `PictureBox`，只能直角）
- `NavBtn`：圆角胶囊导航项 + 左侧强调条
- `RoundField`：圆角输入框宿主（TextBox 自身无圆角能力）
- `RoundCombo`：圆角下拉框。**原生 ComboBox 的箭头由系统绘制，深色主题下是刺眼白块**，
  还会破坏圆角观感 —— 自绘字段 + chevron + 用主题化菜单做下拉面板
- `RoundCheck`：圆角复选框（同上，系统方框在深色下是白块）

配套：`Theme.Round/FillRound/EdgeRound/SoftShadow/ClipRound` 与 `ThemedMenuRenderer`
（右键菜单、下拉面板、托盘菜单统一走主题色）。

#### ② 深色主题（可选，一键切换）

`Theme` 的 350+ 处引用全部集中在 `Theme.X`，所以做成双调色板只需一个开关：

- 浅色保持原有观感（输入底改极浅灰：纯白面板上的纯白输入框等于看不见边界）

#### ④ 封面：为什么"有的没有封面"

实测（2026-09-14）对用户库里 4 个拿不到封面的 Steam appid 做**多主机多路径穷举**：

```
appid 2483190   library_600x900 404 / header 404 / capsule 404 …  library_hero 200 (250KB)  ← 有！
appid 3527290   同上 → library_hero 命中 (351KB)
appid 3548580   同上 → library_hero 命中 (219KB)
```

### ㉔ 2.6.1：重绘加固 + 生成卡重做 + 无封面游戏联网取图（2026-09-14）

用户反馈三条：**侧栏出现黑框、文字重影、"像叠了好几层"**、**封面参差不齐**、**标题重复 + 旁边多了条滚动条**。

#### ① 「旁边那条滚动条」—— 直接原因确认并修掉

侧栏用的是 `FlowLayoutPanel`，它的 **`AutoScroll` 默认为开**。窗口偏矮（或侧栏内容变高）时，
它会在侧栏右侧冒出一条竖滚动条 —— 就是截图里"旁边那条"。侧栏本来就不该滚动，直接：

```csharp
flow.AutoScroll = false;
flow.HorizontalScroll.Visible = false;
flow.VerticalScroll.Visible = false;
```

矮窗口（520px 高）离屏渲染复验：侧栏再无滚动条。

#### ② 「黑框 / 文字重影 / 像叠了好几层」—— 按正确做法加固，但**没有 claim 根因**

这类现象是"控件自己的矩形没被画满、留下上一帧残留"。自绘控件确实必须遵守一条纪律：

> 一旦设置 `UserPaint + AllPaintingInWmPaint`，WinForms **不再帮你擦背景**（`WM_ERASEBKGND` 被跳过），
> 控件必须把自己的整块矩形画满 —— **包括圆角之外那点角落**。

所以本版给 9 个自绘控件（`FlatBtn / NavBtn / RoundField / RoundCombo / RoundCheck / HeadBox /
Sec / GameCard / CoverBox`）统一在 `OnPaint` 开头铺满自身矩形，并加上 `ControlStyles.Opaque`
（自己铺满就不需要父级再画一遍，同时减少闪烁）。

**但要说清楚**：我做了**反向测试**（故意移除 NavBtn 的背景填充再渲染），
**离屏探针并没有复现出黑框** —— 因为 `DrawToBitmap` 走 `WM_PRINT`，仍会铺一次背景，
这类重绘撕裂它抓不到（这是探针的真实盲区，写在这里免得以后误信）。

所以这一条是"按正确做法落地"，不是"已验证的根因"。同时补了两处能确认的重绘加固：

- 窗体与 `root / main / side / foot / content` 容器统一开启双缓冲（Panel 的 `DoubleBuffered`
  是 protected，通过反射设置）—— 拖窗、切页、缩放时的撕裂残影会明显减少
- 侧栏不再有滚动条（见 ①）

**如果装上 2.6.1 后仍能复现**：请再截图，并顺便告我"鼠标动一下/缩放一下窗口后是否消失" ——
能消失就是重绘撕裂，不消失就是布局或绘制错误，两条线的查法完全不同。

#### ③ 封面「参差不齐」—— 生成卡 v3（深色设计感）

v2.6.0 的生成卡是**亮青色渐变 + 浮在中间的小图标**，跟真实盒装封面（基本都暗调）摆在一起
就显得空、像贴纸。v3 改成：

- 底色换成**一族深色渐变**（深靛/深蓝/深青/深紫，低明度），按名字哈希取一组 —— 同款游戏颜色恒定
- 中央品牌色**辉光**把图标"托"起来
- 图标画成 **18px 圆角的磁贴**（占宽 62%），带投影与 1px 亮描边 —— 看起来像真正的应用磁贴
- 斜向高光 + 底部压暗收边

#### ④ 无封面游戏：联网取图（新能力）

封面来源现在是**三级回退**：

| 级别 | 来源 | 说明 |
|---|---|---|
| ① | Steam 官方 CDN | 按 appid 试 7 种官方尺寸，实测直连可用 |
| ② | 按名字搜 Steam appid | 走 steamcommunity，需要代理 |
| ③ | **联网搜图兜底** | Bing 图片搜索，只取竖版大图；会访问任意 https 图片站 |

实现要点：

- Bing 结果里图片直链的形式实测是 `&quot;murl&quot;:&quot;https://…&quot;`（JSON 被 HTML 转义过）。
  **用这个 HTML 实体当定界符，源码里就一个转义双引号都不用写** —— v2.6.1 头一版就是在这儿
  写坏了正则，编译器报 `CS1010 常量中有换行符`。
- 三重过滤：域名黑名单 + 最小尺寸（500×640）+ 竖版比例 **0.58~0.78**。
  初版放宽到 0.95，结果"无畏契约"收到一张**三格拼图**宣传图 —— 收紧后这类东西被拦住。
- 入口：卡片右键「**联网搜寻封面**」单款重抓；「获取封面」批量时作为最后一步；
  「重新下载官方封面」也带这一步兜底。

**实测（本机 16 款库）**：5 款原本没封面的游戏全部拿到真实主视觉 ——
原神（官方 600×900 竖版 key art）、绝区零（1.4MB）、鸣潮、卡拉彼丘、无畏契约。

### ㉚ 2.10.0：自管滚动（修「切全屏后点不动下面那排」）+ 界面复刻 DLSS 5 Swapper（2026-09-15）

#### ① 真凶不是命中测试，是 WinForms 的滚动区缓存（这次彻底换掉 AutoScroll）

用户截图：「切全屏后无法选下面的游戏了」。用新增的 `hit` 模式探针按"先窗口→再全屏→再退回"
的真实操作顺序复现，拿到硬证据：

```
== ① 窗口 1180x1000   Pg 960x909   AutoScrollMinSize={0,1213}  DisplayRect=943x1213   滚轮可达
== ② 改成 1920x1080     Pg 1700x989  AutoScrollMinSize={0,741}  DisplayRect=1700x989   （内容装得下）
== ④ 退回 1180x1000     Pg 960x909   AutoScrollMinSize={0,1213} DisplayRect=**1686x892**
```

第 ④ 步是病灶：`DisplayRect.Width=1686` 而客户区只有 **960**，`Height=892` 正是客户区高度
—— WinForms 认定"没有东西要滚"，于是**竖滚动条消失**（`VScroll.Visible=False`，
尽管内容 1213 > 视口 892），`AutoScrollPosition` 也设不动。下半页既看不到也点不到。

来源是 `LayoutOnce` 里那句 `AutoScrollMinSize = new Size(0, 1)` 的"先复位"：
它会让 WinForms 用**当时的子控件并集**去重算 DisplayRectangle，而那一瞬间子控件还是全屏布局
（宽 1636）留下的旧几何 → 缓存下 1686×892，之后再没人纠正它。

**修法不是再补一层矫正，而是不再把滚动交给 WinForms**：

- `AutoScroll = false`，`Pg` 自己持一个 `VScrollBar`（`Dock=Right`）；
- `LayoutOnce` 把子控件整体放在 `y - ScrollY`（子控件是**真的被移动**的，命中测试自然跟着走）；
- `SyncScrollRange()` 按"内容总高 vs 视口高"给滚动条定价；
- `Reflow()` 里那圈 `PerformLayout()` 矫正**整段删掉**（它存在的唯一理由就是刷 WinForms 的缓存）。

顺带修掉一个坑：`ScrollBar.Value` 的 setter 越界时是**抛 ArgumentOutOfRangeException**、
不是夹紧 —— 传 `int.MaxValue` 会被 `catch` 吞掉，滚动位置纹丝不动。`SetScrollY()` 现在自己夹紧。

验收（探针 `hit` 模式，同一会话跑完五个阶段）：

|---|---|---|---|
| ① 窗口 1180×1000 | 0 | 0 | 1 |
| ② 切全屏 1920×1080 | 0 | 0 | 0 |
| ③ 全屏下滚到底 | 0（内容装得下，正确） | 0 | 0 |
| ④ 退回 1180×1000 | 0 | 0 | 1 |
| ⑤ 窗口下滚到底 | **304**（= 内容 1213 − 视口 909） | **0** | **0** |

### ㉛ 2.10.1：三处视觉/绘制修复（2026-09-15 当晚）

用户截图三张，逐个查实：

#### ① 深色下滑条是纯白的 —— 原生 VScrollBar 不吃 uxtheme

uxtheme 的 `DarkMode_Explorer` 对**独立滚动条控件**不生效（只对 Panel/ListView/TextBox 那类有效），
所以 2.10.0 新加的原生 `VScrollBar` 在深色下就是一整条白底。既然滚动已经自己管了，
滚动条也自绘：新增 `FlatScroll`（10px 细条 + 圆角滑块 + 悬停变亮 + 拖动/点轨道翻页），
取值对齐 DLSS 5 Swapper 的 `--scroll`（浅色 `rgba(16,24,32,.20)`、深色 `rgba(255,255,255,.13)`）。

#### ② 深色下 ListView 表头是白条 —— 表头是**独立子窗口**

`ListView` 的表头是单独的 `SysHeader32` 子窗口，只给 ListView 本身设主题**它不跟着变**。
必须在句柄创建后单独染一次：`SetWindowTheme(SendMessage(lv.Handle, LVM_GETHEADER, 0, 0), "DarkMode_Explorer", null)`。

#### ③ 全屏后内容顶部一条被压扁的卡片行 —— 残影，不是布局算错

新增探针 `capture` 模式（`GetDC` + `BitBlt` 直接读**窗口表面**）复现：
`1180x1000 → 1744x537`（用户那次 1744×537）之后，卡片网格在被压扁的中间态位置画过一帧，
**那一块之后再没被失效**，于是留在表面上。

> ⚠️ 这正是为什么此前所有修正都"看不到问题"：`DrawToBitmap` 会强制整棵树重绘，
> **残影类 bug 在它面前是隐形的**。要验这类问题必须读真实表面。

根因：这套自绘控件族（`Pg` / `Sec` / `CardGrid` / `GameCard` 全是 `Opaque` + `UserPaint` +
`AllPaintingInWmPaint`）**父容器不擦背景**，孩子移动时留下的旧像素没人负责擦；
而 WinForms 的失效区在连续 resize / 最大化那一帧会被系统重绘吞掉。
修法：`MainForm.OnResize` 里用 `BeginInvoke` 等布局落定，再 `Invalidate(true)` + **`Update()`**
把整棵立刻刷一次（`Update()` 是同步刷，光 `Invalidate` 不够）。

**验收**：同一组 `capture` 序列重跑，顶部那条卡片残影消失；深色 p1 表头变深、深色 p3 滚动条变细变深。

但你截图里的东西不是"画完没擦"的残影 —— 已查明 `Sec` / `HeadBox` 的 `OnPaint` **本来就铺满整块矩形**（第 932/1269 行），
所以那条带只可能是**网格控件本身被摆到了错误的 Y、且高度只剩十几像素**：子控件会被裁到父容器范围内，
露出来的正好是每个封面的顶端一条 —— 与截图完全吻合。也就是说，这是**布局卡在了错误状态**，不是绘制问题。

#### 找到的机制

`Pg.Reflow()` 有一道早退闸，为了避免"点一下卡片就跳回最上面"而加：

```csharp
if (lastCount == secs.Count && lastW == ClientSize.Width && lastTotal == ContentHeight()) return;
```

问题在于 `lastTotal` 等三个缓存数是 **`LayoutOnce()` 跑完之后**才写入的。万一某次布局在中途被打断
（或某个分区高度被算成 0），缓存可能已经写成"最终值"而控件还停在坏位置上 ——
此后每次 `Reflow()` 都命中早退闸，**坏布局永久留在屏幕上**。这正好解释"出现后不消失"。

#### 三处修复

1. **早退闸从"盲信缓存"改成"缓存一致 **且** 几何正确"**：新增 `Pg.GeometryLooksRight()`，
   逐个核对 head/sec 的 `Top` 是否等于算出来的累积位置、高度是否塌陷（head < 20px / sec < 30px）。
   不通过就强制重排，并写一条 `[布局自检]` 日志（含 Pg 尺寸、内容高、每个分区的高:位置、ScrollY）。
2. **`LayoutOnce` 对塌陷高度就地纠正**：分区高度小于 30px 时按最小高度重设并重跑一次 `DoLayout()`。
3. **`OnResize` 改成两遍「重排 + 整树重绘 + 自检」**（第二遍排到下一轮消息之后）——
   2.10.1 只做了一遍，而"布局落定"可能比那次重绘更晚。另加 `MainForm.CheckLayoutHealth()`，
   **只在几何异常时**写日志，便于在真机上留证。

#### 验证：把那条带**人为造出来**，看能不能自愈（探针 `selfheal` 模式）

| 造法 | 结果 |
|---|---|
| A) 只把分区搬到 y=18（**高度不变 → 三个缓存数全都一致**，旧代码必然早退卡死） | 破坏后 Top=18 → `Reflow()` 后 **Top=245（期望 245）**、网格 Top=4（期望 4）→ **PASS** |

回归：残影差分 9 个时序全部 0 差异；摆放矩阵 6 尺寸全部正常；7 页 × 浅/深 14 张渲染全过。

### ㊱ 2.10.7：「卸载 / 部署」改造成「切换方案」（改名停放，秒级来回）

用户要求：**别再用「卸载」这个说法**，而且要在两套帧生成方案之间随时来回切换。

原来的语义确实不对 —— 「卸载」在实现里会**移动/删除运行库文件**，用户看到这个词自然以为"装不回来了"；
而它也确实会带走 NR 模型与 SM86 运行库（用户已因此误点两次）。改造后：

| 旧 | 新 | 实际动作 |
|---|---|---|
| 部署 / 卸载 | **切换到本方案** / **停放（回到原生）** | 切换 = 把别人的入口代理改名成 `<入口>.parked.<方案>`，把自己的改回原名；**一个文件都不删** |

实现（`Dlssg.cs` 新增 `Plan` 类）：

- `Plan.OwnerOf(path)` —— 按文件名后缀 + 体积双重判定一个 DLL 属于哪套方案
  （>20MB = OptiScaler 入口、17–20MB = 0.3.0 入口、15–17MB = 早期 `dlssg_for_sm86`）；
  **不是代理就返回空串，绝不碰游戏自带文件。**
- `Plan.Current(gameDir)` —— 先看主入口，主入口被停放就扫全部入口名
  （`dxgi / d3d12 / version / dinput8 / winmm / winhttp / dbghelp`），返回
  `opti` / `030` / `legacy` / `none` 之一。
- `Plan.ParkOthers(gameDir, kind, keep)` —— 把"不是目标方案"的入口代理改名停放。
- `Plan.SwitchTo(gameDir, target)` —— 目标方案文件已在目录（只是被停放）→ **只改名，秒完成**；
  不齐才走一次真正的安装。

界面上两处「当前状态」也都改成读同一个 `Plan.Current`，所以不会出现"两个区块各说各话"：

```
当前：方案 A · OptiScaler 注入（dxgi.dll 槽位）  ← 本方案在用
当前：DLSS MFG 0.3.0（d3d12.dll 槽位）          ← 切到本方案会把它改名停放
当前：原生（所有代理都已停放）                    ← 代理已停放，游戏跑原生
```

**验证**：`tools/plan_probe.cs`（`_run_planprobe.py` 编译运行）在 `%TEMP%` 沙盒里造
**假鸣潮 / 假绝区零目录**，真跑切换逻辑，**10 条断言 ALL PASS**：

| 断言 | 结果 |
|---|---|
| 方案 A 在用 → `Current = opti` | PASS |
| 切到 0.3.0 → `Current = 030`，且 A 的入口被改名为 `.parked.opti` | PASS |
| 再切到"原生" → `Current = none`，入口变为 `.parked.030` | PASS |
| 再切回方案 A → `Current = opti`，`.parked.opti` 改回原名 | PASS |
| **全程文件总数不变（7 → 7）、没有任何文件消失** | PASS |
| 只装旧版代理 → `Current = legacy`（早期 `dlssg_for_sm86` 也能识别） | PASS |
| 绝区零槽位（`d3d12.dll`）同样可切、可切回 | PASS |

同时清掉界面上残留的「卸载」措辞（含数据目录说明、0.3.0 的互斥守卫、各条回执）。

**一句话选型（用户问的）**：

> **两个二游都用「方案 A · OptiScaler 注入」** —— 绝区零只能用它（它的 DLSS / 帧生成选项就是靠这套的显卡名伪装出现的）；
> 鸣潮也用它（同一套同时给「帧生成」和「DLSS 5 神经渲染」，且实测 6X 可用）。
> 「DLSS MFG 0.3.0」留着备用：**它不含 NR，也不做显卡名伪装**，换过去等于功能降级。

### ㊲ 2.10.8 / 2.10.9：0.3.0 到底"只能给 3A 用"吗 + 措辞一致性收口

游戏侧调用不变，所以任何会请求 FG 的游戏都能用。

真正的分水岭是**单机 / 网游**（作者自己也是这么分的）：

| | 单机 3A | 网游（绝区零 / 鸣潮） |

本工具带的就是 310.9 / 6X 那一版。顺带两个前提：视频强调要开「GPU 硬件加速计划」（本工具

### ㊳ 2.11.0：0.3.x 开放给任意游戏（3A 单机）+ 修掉"把 maxGeneratedFrames=5 写进旧版代理"的致命 bug

用户纠正 + 两个实测问题：
> 这个也能给 3A 用的，我看视频就是这么说的，要不然现在这个状况我的 2077 只能开 4 倍帧生成。地平线 6 卡在这进不去游戏。

**① 我上一轮的说法没错，但工具根本没给这条路。** `XeMfg.Detect()` 只认绝区零 / 鸣潮，
其余游戏一律"不在支持列表" —— 选中 2077 / FH6 时 0.3.0 区块只会显示「原生（所有代理都已停放）」，
等于把作者文档里"单机只放两个文件"的那条路堵死了。本轮开放：

- `Plan` / `XeMfg.TargetDir` 支持 `kind == ""`：落地目录 = 扫描认定的 exe 所在目录。
- `Dlssg030.InstallGeneric(dir, entry, maxFrames)`：只放**入口 + dlssg_sm86.ini 两个文件**，
  不覆盖游戏自带的 nvngx（实测 CP2077 的 `nvngx_dlssg.dll` 7,607,336、FH6 的 7,499,376 都比包内那份新）。
- 界面新增「通用游戏入口（3A 单机）」下拉：`version.dll / winmm.dll / dbghelp.dll / dinput8.dll / dxgi.dll / d3d12.dll`
  （作者 `alternatives/README.md` 的 6 选 1）；游戏不加载默认入口时换一个即可。
- 方案 A 仍然只对绝区零 / 鸣潮开放 —— 选中其它游戏时该区块会直说原因。

**② 真凶：`应用参数` 把 5 写进了装着旧版代理的游戏 → FH6 卡死。**

旧版 `dlssg_for_sm86`（14.94 MB，内嵌 310.1 运行库）只认 `MaxGeneratedFrames = 1..3`。
而 `DoApplyFgCfg()` 里的条件只排除了「0.3.0 部署态」，**没有排除旧版代理**，于是：
用户在帧生成页把「最大生成帧」设成 `5 · 6X` 并点「应用参数」→ 工具把
`MaxGeneratedFrames=5` 写进 FH6 的 `dlssg_sm86.ini`（261 B 旧模板）→ 代理报
`{"event":"configuration_error","message":"Invalid INI integer"}`（`dlssg_sm86\logs\native_10932.jsonl`，只有这一行）
→ **FH6 停在加载界面进不去**。同一个动作也写到了 CP2077 的**根目录**（那里不是渲染 exe 目录，无害）。

修法：
1. `DoApplyFgCfg()` 改成**逐游戏先认代理、再决定写什么**（`Plan.OwnerOf`）：
   目录里没有我们的代理 → **一律不碰**（并计数报告）；认出来是旧版 → 用新增的
   `Dlssg.BuildIniFor(m, log)`，上限**夹到 3**（并在日志里说明"要 6X 请先升级到 0.3.x"）；
   认出来是 0.3.x → 走 `Dlssg030.SetMaxFrames`（只改一行，保留 `[General]` 等键）。
2. `Plan.LooksProxy` 下限 15 MB → **14 MB**：旧版代理是 14.94 MB，
   按 15 MB 划界会**整类漏掉** —— 既认不出它，也拦不住"两个代理同时生效"。
3. `Plan.OwnerOf` 的 0.3.x 阈值 17 MB → **16 MB**：0.3.x 入口是 `17,529,120 B = 16.72 MB`，
   原来的 17 MB 阈值会让它掉进 legacy（**探针新断言抓到的**，不是猜的）。

**③ 已直接修复的两台机器现场**（本次会话内完成）

| 游戏 | 处理 | 结果 |
|---|---|---|
| ForzaHorizon6 | 停放旧版 `version.dll`（14.94 MB）→ 换成 0.3.x 的 `version.dll`（17,529,120 / SHA `A22D2453…`）+ 2099 B 出厂 INI | 生效代理只剩一个，`[General] Enabled=1`、`MaxGeneratedFrames=5` |
| Cyberpunk 2077 `bin\x64` | 同上，并把同目录的旧版 `winmm.dll` 改名停放（**两个代理同时生效是作者明令禁止的**） | 同上；根目录的历史残留 ini 也移走 |

备份一律就地保留（`version.dll.bak-<时间戳>`、`winmm.dll.parked.legacy`），可随时还原。

**④ 验证**：`tools/plan_probe.cs` 扩到 **10 组 20 条断言，全部 PASS**，新增三组专门盯这次的坑：
- 14.94 MB 的旧版代理必须被认成 `legacy`（旧代码认不出）；
- 通用游戏（假 FH6 目录）从旧版切到 0.3.x：入口换成 17,529,120、ini 换成含 `[General]` 的出厂版、
  **游戏自带的 `nvngx_dlssg.dll` 未被覆盖**、旧代理改名为 `.parked.legacy`、还能停放回原生；
- `BuildIniFor(5)` 必须写出 `=3`（写 5 就是本次事故），`BuildIniFor(0)` 兜到 1。

**⑤ 顺带说明 6X 的边界**（作者 README 原文口径）：上限由**游戏侧插件**决定 ——
游戏自带较新插件（支持 Dynamic MFG）时，装 310.9 + `MaxGeneratedFrames=5` 可跑到 6X；
游戏只支持 4X 时，本项目**无法**把它抬上去。作者实测表里 2077 与 FH6 都在"可开 4X"那一档；
装好后 `dlssg_sm86\logs\native_*.jsonl` 里的 `generated_count` 会直接给出答案（3 = 4X，5 = 6X）。

### ㊴ 3.0.0：UI 不再挡视线 + 「方案推荐」+ 长文案搬到说明页 + 功能缺口盘点

用户三条要求：① UI 有阻挡、② 插件太多希望直接给推荐、③ 解释文字太多挡视线（并顺手找别的 bug）。

#### ① UI 阻挡的真凶：`Sec` 的行布局用了固定标签宽

`DoLayout()` 的 KRow 分支里，控件位置写的是

```csharp
if (it.B != null) { it.B.Left = (it.A == null) ? padX : padX + labelW; ... }   // labelW = Theme.S(102)
```

`labelW` 是**固定值 102px**，而标签是不透明底色（`BackColor = contentBg`）。
标题一旦比 102px 长，就会**直接盖住右侧控件** —— 用户截图里那个只剩 `n.dll` 的下拉就是这么来的
（`version.dll` 左半被「通用游戏入口（3A 单机）」这个长标题糊掉了，不是控件窄）。

修：标签宽度按**真实文字量**算（`Math.Max(labelW, it.A.Width + 8)`），控件放不下就缩宽（下限 48px），
宁可窄也不重叠。另外把「通用游戏入口」这一项**单独占一行**（`Block` 铺满），彻底避开挤压。

#### ② 方案推荐：按档位给一句话结论

新增区块「方案推荐 · 按游戏类型挑」，两行动态文字由 `Dlssg.RecommendLine(DlssgGame)` 生成
（档位取自配置里已有的三张名单：二游 / 3A / 竞技，不靠猜）：

| 档位 | 推荐 | 理由（原文摘） |

| 竞技网游（CS2 / 无畏契约 / 三角洲） | **不建议装**（只做电源 / 加速包联动） | 内核反作弊，注入类封号风险自负，收益也不值当 |
| 二游（绝区零 / 鸣潮） | **方案 A · OptiScaler 注入** | 绝区零的 DLSS 选项靠它的显卡名伪装才会出现；鸣潮同一套同时给帧生成 + DLSS 5 NR |

让 3A 游戏装没装成功在列表里一眼可见。

#### ② 绝区零：方案A 的代理**从未被加载过**（此前所有判断的前提错了）

| 证据 | 结论 |

### ㊸ 3.1.0 补充：「判定要对后续新添加的游戏生效」（用户要求）

用户一句话点出的是**判定生命周期**问题：前面那套判定（是不是游戏 / 有没有可接管的调用 / 该装哪套）
只在"当时那份库"上成立 —— 以后新下载的游戏得靠用户自己去改名单，等于没生效。

查出来的三处缺口（都在"新加的游戏"上暴露）：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | `Program.AutoCategory`（联动档位）**完全不看游戏库**，只查四张静态名单，而且**未命中一律 `return "fps"`** | 新装的游戏被判成竞技网游 → 玩它时 **UU远程 被暂停**（和"启动二游也杀远控"同源） |
| 2 | `AllGameProcesses()` = 四张名单的并集 | 新加的游戏**根本不算"游戏"**：电源联动 / 加速包 / 定时器 / 亲和性 / P 核绑定全轮不到它，手动档位下拉里也看不到它 |
| 3 | `MergeScan` 只对"手动添加"的条目重探能力；`FillGameList` 又按**对象引用**比较高亮 | 绕过扫描进来的条目带着过期字段；每次扫描（对象全换新）后**选中项丢失**、推荐块继续渲染旧对象 |

修法（核心思路：**判定只留一个计算点，两个消费者读同一个值**）：

| 位置 | 改动 |
|---|---|
| `Dlssg.Library` | 新增静态引用，**只由 `MergeScan` 写入**（唯一入口，避免多处各维护一份而走样） |
| `DlssgGame.RecCat` | 每次合并重算并缓存分类 —— `AllGameProcesses()` 在每次进程快照里被调十几次，不能在里面做目录探测 |
| `MergeScan` | **每一条**都重探能力字段并重算分类（不再只探手动条目）；盘根目录跳过（`Inspect` 会递归整块盘） |
| `Dlssg.FindByProcess` | 按进程名找库条目（先比 exe 名，再退一步比目录末段） |
| `Dlssg.LinkCategory` | 把推荐分类映射成联动档位；`platform → ""`（不是游戏，不参与任何联动） |
| `Core.AutoCategory` | **先问游戏库**（与「方案推荐」共用同一套规则）→ 再静态名单兜底 → **未知不再默认 fps** |
| `Core.AllGameProcesses` | 并入库里"是游戏"的条目（排除对战平台），并全部改成 null 安全 |
| `Core.GameDisplayName` | 新游戏的显示名取自库标题（否则手动档位下拉里会出现 `REDprelauncher` 这类原始进程名） |
| `Ui.FillGameList` | 重建列表后按**目录**重新定位 `selected`（否则高亮丢失、推荐块渲染旧字段） |

**顺手修掉两个真 bug**（都是探针先抓到、不是我推出来的）：

1. **`Cfg.MmoGames` 为 null 时 `AutoCategory` 直接抛 `NullReferenceException`** ——

`icon\candidates\_preview_crop.png`、`_preview_headroom.png`、`_preview_32px.png`。

**水印的处理方式：避开，而不是擦除。** 水印在角色之外的背景区，所以把它裁到画面外即可 ——
没有做任何修补/美化，构图与像素来自原图本身。这条很重要：生成端加的"AI生成"水印，
能用裁切解决就不要用修复工具，前者不引入任何发明出来的像素。

#### ③ 坑：全部帧都用 PNG 压缩 → PIL 读得动，Windows 读出来是**垃圾**

第一版 ICO 容器我把 7 帧**全写成 PNG**（Vista+ 支持，且体积小）。PIL 回读完全正常，
但走 Windows 自己的图标 API 一验就露了：

```
取样 RGB(81,26,235)  ← 紫色
取样 RGB(197,186,144) ← 土黄
角 alpha = 112 / 95 / 93 / 189   ← 圆角应该接近 0
```

**我的图里根本没有紫色和土黄。** 原因是 **GDI+ 对"非 256 的 PNG 帧"不认** ——
它会按 DIB 的布局去解 PNG 数据，于是整幅错位成噪声。

**正解（业界标准做法）**：

| 帧 | 容器格式 | 体积 |
|---|---|---|
| 16 / 24 / 32 / 48 / 64 / 128 | **DIB**（40 字节 BITMAPINFOHEADER + 自下而上 32 位 BGRA + 1bpp AND 掩码） | 1.1KB … 67.6KB |
| 256 | **PNG** | 56.8KB |

改完再验，取样变成角色真实的 `RGB(5,174,110)`、四角 alpha 0–3、**exe 内嵌图标与文件帧逐像素 0 差异**。

> ⚠️ **教训（这条最值钱）："第三方库能读"不能作为验收依据。**
> PIL 对 ICO 的宽容度远高于 Windows，PNG 帧它照读不误。
> 交付给 Windows 的图标，必须走 **Windows 自己的 API**（`System.Drawing.Icon` /
> `ExtractAssociatedIcon`）验一遍，并把 ICO 目录**按字节解析**验一遍容器结构。
> 新增 `tools/icon_probe.cs` + `tools/run_icon_probe.py` 固化这两条（**40 条断言 ALL PASS**）。

#### ④ 另一个实测结论：GDI+ 请求 256 会回退到 128（不是文件问题）

用三种容器分别试（我们的 PNG256 / 我们的 DIB256 / **上一版旧图标**），
请求 256 **全部返回 128** → 是 `System.Drawing.Icon` 的上限。Explorer 走 shell 自己的加载器，
能用到 256 帧；`Program.GetAppIcon()`（托盘）本来只用 16/32。所以这不是缺陷，探针里如实标注放行。

### ㊾ 3.3.1：驱动门槛纠正 —— 「≥616.56」只对 RTX 50 成立，别为 NR 升级驱动

用户问「616.56 或者以上的驱动有哪一个适合 3060ti」。查完之后发现 **我在 3.3.0 里把这条读错了**，
并且写进了源码 6 处 + 本文档 2 处。这是本轮最重要的产出：**纠正一个会导致误操作的结论**。

#### ① 我错在哪

`DLSS5-Swapper`（`rakanki911`，★4.8k）的 `src/core/install-guards.js` 里有两个常量，
我上一轮只摘了第一个去看：

```js
const OPTI_DRIVER = 61656;          // 我据此写成"驱动 ≥616.56 是硬门槛"  ← 错在这
const NEURAL_FAULT_DRIVER = 61664;  // 这个才是"任何 N 卡都要避开"的
```

但 `OPTI_DRIVER` 的**判据**是 `driverSupported`：

```js
function driverSupported(rows) { return rows.some(row => blackwell(row) && driverNumber(row) >= OPTI_DRIVER); }
//                                                      ^^^^^^^^^^^^^^^^  ← 必须是 RTX 50
```

而它上方的注释写得更直白（原文）：

> Two separate questions, because only one of them is a hard requirement. The card is: DLSS-NR runs on the
> RTX 50 path. **The driver is not**: the model file (`nvngx_dlssnr.dll`) ships with this app rather than
> being taken from the installed driver, so **an older driver still runs an OptiScaler install** — which is
> what people who rolled back off 616.x to keep RenoDX working are seeing.

→ **模型随应用提供、不取自已安装驱动，旧驱动照样能跑。** 对 3060 Ti（Ampere）根本不是门槛。

#### ② 那真正该避开的是什么

```js
// Measured upstream by the Feeder author across three machines: with the RenoDX DLSS 5 consumer (v4.6 and
// v4.7), every neural evaluate faults inside NVIDIA's own NGX runtime on 616.64 and 616.86, while 616.56
// completes. Reported as DLSS5-Feeder issue #54. This only warns ...
const NEURAL_FAULT_DRIVER = 61664;
function driverNeuralFault(rows) {
  return (rows || []).some(row => /nvidia|rtx|gtx/i.test(row.name) && driverNumber(row) >= NEURAL_FAULT_DRIVER);
}
```

注意它的正则是 `/nvidia|rtx|gtx/i` —— **对任何 N 卡生效，不限于 50 系**。
所以约束是「**≥616.56 且 <616.64**」，也就是**只剩 616.56 一个版本**。

#### ③ R616 版本序列与对 3060 Ti 的适配

| 版本 | 日期 | 3060 Ti | NR | 备注 |
|---|---|---|---|---|
| **610.88**（本机） | 07-22 | ✅ | 能跑（模型不取自驱动） | **现状，已实测鸣潮 6X + NR 可用过** |
| **616.56** | 08-26 | ✅ 支持清单内 | ✅ completes | 唯一"达标且能跑完"的版本 |
| **616.64** | 09-03 | ✅ 支持清单内 | ❌ fault | NBA 2K27 首发 DLSS 5（那是给 50 系的） |
| 616.86 | 09-04 | ✅ | ❌ fault | Hotfix，不通过 NVIDIA App 推送 |
| **616.92**（最新） | 09-09 | ✅ | ❌ fault | 007 First Light 等 |

#### ④ 结论：**不要升级**（对这台机器）

不是"哪个版本最好"，而是**唯一达标的那版恰好有两个对你致命的已知问题**：

| 616.56 的已知问题 | 对这台机器的影响 |
|---|---|
| 升级后**远程桌面（RDP）黑屏** | 🔴 你常驻 **UU远程（GameViewer）** |
| 升级后**无法创建虚拟显示器** | 🔴 远控/虚拟屏软件依赖这个 |
| 「优先最高性能」电源模式可能不生效 | 🟡 工具 NVAPI 竞技档就写这一项 |

修掉前两条的 616.86 hotfix，以及最新的 616.92，**都 ≥616.64 → NR 会 fault**。
也就是说：想同时要「NR 可用」和「远控正常」，**在 R616 里无解**。

而且更根本的一点：**这次鸣潮 GPUCrash 不是驱动版本造成的** —— 崩溃真因是 NR 与 4X 帧生成同开
（上游明写其约束「were paid for with device hangs」），升级驱动解决不了。NR 已改为默认关闭并做成开关。

#### ⑤ 已同步修改的位置

源码 6 处（`Core.cs` 字段注释 / `Ui.cs` cbNr 注释 / `Ui.cs` 说明页前置条件 / `Dlssg.cs` `NrHint` /
`Dlssg.cs` 说明页 / `Dlssg.cs` `PrereqReport`），以及本文档 2 处。

其中 `PrereqReport` 的驱动行改为调用新增的 `Dlssg.NoteDriver(drv)`，按档位给结论：

- `< 591.86` → 低于作者下限，先升级
- `591.86 ~ 616.55` → 正常区，**明确告诉你"不必为了 NR 升级"**
- `616.56` → 唯一既达标、NR 又能跑完的版本
- `≥ 616.64` → 警告 NR 会 fault，要用 NR 就回退到 616.56

> **教训（写给以后的我）**：看到源码里的阈值常量，**必须连同它的判定函数一起读**。
> 只摘常量不读判据，就会把一个"只针对 A 类硬件"的门槛说成"人人都要满足"，
> 然后据此劝用户做一个既没收益、又带已知风险的升级。

### ㊿ 3.3.2：分享友好化 —— 出厂模板去个人残留 + 推荐引擎显卡代际门禁

用户问「能分享给别人吗？会根据别人的显卡和电脑状况来做推荐吗」—— 核实后两个答案都需要补课。

#### ① 安装包模板里的个人残留（会直接坑到别人）

`installer\Fluxion.iss` 原来打的是**项目根 config.json** —— 那是便携模式配置，里面带着本机个人设置：

| 键 | 本机值 | 对别人意味着 |
|---|---|---|
| `dlssg.useProxy=true` + `proxy=http://127.0.0.1:7890` | 本机 FlClash | **「下载运行时」必失败**（别人没有这个代理） |
| `gameAware.remoteApps` | 用户的 UU远程 exe 路径 + 长注释 | 机器特定，无意义 |
| `ui.closeToTray=true` | 用户点过「记住我的选择」 | 别人点 X 直接收托盘且不知为何 |
| `cleanup.killList` | 用户的 MuMu/百度网盘名单 | 个人习惯 |
| `dlssg.maxGeneratedFrames=3` | 用户选的 4X | 出厂应为 2 |

修：新增 **`installer\config.default.json`**（由根 config 生成、上述键全部回出厂值），`.iss` 改指向它。
根 config.json **原样保留**（它仍是便携模式配置）。安装器语义不变（`onlyifdoesntexist`，不覆盖已有配置）。

#### ② 推荐引擎的显卡代际门禁（之前完全没有）

`BuildRec` / `RecommendCategory` 原来只看**游戏类型与组件**，不看**对方的卡**：
给 RTX 40/50 用户照样推「一键应用 0.3.x + 伪装」——他们原生就有帧生成，且把 4090 改名 5090 是**降级**；
给 GTX / AMD / Intel 用户也照样推荐 —— 装了也不会有任何选项。

新增（`Dlssg`）：`GpuTierFromName(name)`（纯函数，可测）→ `GpuTier()`（读 `Program.GpuDisplayName`，
unknown 不缓存——WMI 探测可能未完成）→ `GpuGateRec(tier)`。`BuildRec` 在 platform/fps 分支**之后**、
gacha/aaa 分类**之前**过门禁（platform/fps 本来就"不推荐安装"，结论与显卡无关，保持不变）：

| 对方显卡 | 推荐结论 |
|---|---|
| RTX 40 / 50 | 中性灰「不用装：这张卡原生支持 DLSS 帧生成」+ 点名「伪装对 40 系是降级」，按钮禁用 |
| GTX / 其他 NVIDIA | 红色「用不了：不在 RTX 20/30 系支持范围」，按钮禁用 |
| AMD / Intel | 红色「用不了」+ 指向游戏自带的 FSR3 / XeSS |
| RTX 20 / 30 | 不拦 —— 原有推荐不变（本机 RTX 3060 Ti 实测回归通过）|
| 未识别（探测中/未知） | 不拦 —— 不误伤 |

`PrereqReport`（前置条件检查）补「显卡代际」一行。顺带：`Program.GpuName` 是多变量声明
（`string CpuName = …, GpuName = …`），自研静态检查器只登记首个变量名 → 跨类引用被误报
UNRESOLVED；加单声明属性 `Program.GpuDisplayName` 绕开（不动检查器）。

#### ③ 两个探针教训（这轮各踩一次）

- **补丁脚本 `sys.exit(1)` 在 `save()` 之前** → 前面的 rep 全部没落盘，而后续探针读到的是
  上一轮的旧结果文件，"222 PASS" 是假的。**多步补丁必须先写完再退出；探针结果文件要核对时间戳。**
- **探针加载真实配置** → 用户 `config.local.json` 里 `genericEntry=d3d12.dll`（UI 下拉选过），
  plan_probe section 9 断言 version.dll 必 FAIL。**沙盒探针必须显式固定被测输入**，不该信任宿主机器的配置。

#### ④ 关于分享，还有一件事没做（如实说明）

安装包 **2.6MB，不含帧生成资源包**（0.3.x 签名版 + OptiScaler 套件 ≈ 270MB，在数据目录）。
对方装完后帧生成功能需要资源包才完整；「下载运行时」按钮目前只覆盖旧版运行库的下载源。
